# Пускане през GitHub

Cloudflare следи хранилището и строи сам при всяко бутане в клона, който му
посочиш (Workers Builds). GitHub Actions тук **не публикува** — то само
проверява, че проектът се компилира. Два независими пътя към една и съща
услуга рано или късно качват две различни версии една върху друга.

> Кодът е в PR [#1](https://github.com/radoslav1992/seo-bot/pull/1). Слей го в
> `main` преди да закачиш хранилището, или посочи клона
> `claude/seo-bot-astro-ui-lyle7s` на стъпка 2.

Целият процес минава през браузъра — таблото на Cloudflare и GitHub. Терминал
не е нужен никъде; вариантът с `wrangler` е описан накрая, за тези, които го
предпочитат.

## 1. Базата

Таблото на Cloudflare:

> **Storage & Databases** → **D1 SQL Database** → **Create Database**

Името да е `seo-bot` — точно това стои в конфигурацията и в командата за
деплой. Отвори базата и копирай **Database ID**.

Идентификаторът се вписва в `wrangler.jsonc` направо през GitHub (моливчето
върху файла, после Commit). Не е тайна, а адрес, и стои в хранилището точно
защото Cloudflare строи оттук: връзка, добавена ръчно от таблото, се затрива
при следващия деплой.

Заместителите, които трябва да станат истински стойности:

В `wrangler.jsonc` за попълване има **едно-единствено** нещо:
`d1_databases[0].database_id`, сега нули. Останалите настройки — моделите,
адресът на сайта — се задават от **Settings → Variables and Secrets** на
worker-а и имат стойности по подразбиране в кода, тоест свеж клон тръгва без
нито една зададена. Виж [docs/models.md](models.md) защо е така и защо не
изчезват при деплой.

Workers AI не иска създаване — `"ai": { "binding": "AI" }` е достатъчно.

## 2. Закачането на хранилището

Cloudflare Dashboard → **Workers & Pages** → **Create** → **Import a repository**
→ избираш `radoslav1992/seo-bot`.

| Поле | Стойност |
|---|---|
| Branch | `main` |
| Build command | `npm run build` |
| Deploy command | `npm run deploy:cf` |
| Root directory | *(празно)* |

> **Командата за deploy НЕ е тази по подразбиране.** Cloudflare предлага
> `npx wrangler deploy`; с нея миграциите на D1 не се пускат. Билдът минава,
> деплоят минава, а приложението гърми чак при първата регистрация с „таблиците
> липсват“. Смени я на `npm run deploy:cf`.

`deploy:cf` пуска миграциите **преди** качването и чак после деплойва — за да
не посрещне новият код стара схема. Първият билд ще се провали, ако
`database_id` още е нули; това е нарочно шумно.

> **`name` в `wrangler.jsonc` трябва да съвпада с името на Worker-а.** Сега е
> `seo-bot`. Създаде ли Cloudflare Worker с друго име, изравни ги. Разминаване
> не чупи деплоя през Workers Builds (то качва в закачения Worker независимо
> от полето) и точно затова е коварно: всяка команда на `wrangler` от лаптоп
> после отива другаде, а `wrangler deploy` би СЪЗДАЛ втори Worker.

## 3. Секретите

Worker → **Settings** → **Variables and Secrets** → тип **Secret**.

| Секрет | Задължителен | За какво |
|---|---|---|
| `SESSION_SECRET` | да | Подписва бисквитките за вход. Без него входът връща 503. |
| `TOKEN_ENC_KEY` | да | Шифрова Google refresh токените в базата. Без него връзката с Google е изключена. |
| `GOOGLE_CLIENT_ID` | за GSC/GA | OAuth клиент |
| `GOOGLE_CLIENT_SECRET` | за GSC/GA | същият клиент |

Двигателите за видимост **не искат секрет**: партньорските модели минават през
binding-а `AI` като всички останали и се плащат от сметката в Cloudflare.

`SESSION_SECRET` и `TOKEN_ENC_KEY` ги измисляш ти — дълги случайни низове:

```bash
openssl rand -base64 48
```

**Без терминал** (целият този наръчник минава през браузър): отвори нов раздел
на `about:blank`, натисни F12 за конзолата на браузъра и пусни това два пъти —
веднъж за всеки секрет:

```js
btoa(String.fromCharCode(...crypto.getRandomValues(new Uint8Array(48))))
```

`crypto.getRandomValues` е същият генератор, който браузърът ползва за TLS —
не е `Math.random()`. Излиза 64 знака base64. `about:blank` е нарочно: чужда
страница вижда каквото пише в собствената си конзола.

Форматът няма значение — всеки низ става. `SESSION_SECRET` влиза направо като
ключ за HMAC, а `TOKEN_ENC_KEY` минава през SHA-256, преди да стане ключ за
AES-GCM ([`src/lib/auth.ts`](../src/lib/auth.ts)). Дължината е единственото,
което има значение, и 48 байта са предостатъчни.

**Различни стойности за двата.** Един и същ низ би вързал изхода от профила за
четимостта на чуждите токени — две неща, които нямат общо и се сменят по
различни поводи.

**Запази си копие** (например в мениджър на пароли). Cloudflare не показва
секрет след записа, а `TOKEN_ENC_KEY` е точно този, който не бива да се губи.

Останалите идват от съответната услуга.

> **`TOKEN_ENC_KEY` не се сменя лекомислено.** Смяната му прави вече
> записаните Google токени нечетими и всички потребители трябва да свържат
> акаунтите си наново. `SESSION_SECRET` при смяна просто отписва всички.

### Когато нещо гърми с 500

Неочакваните грешки връщат JSON, не HTML страница, и вървят в дневника на
Worker-а (**Workers & Pages → seo-bot → Logs**, пусни ги и повтори действието).

Ако дневникът не е под ръка, задай временно променливата `DEBUG_ERRORS=1`
(Settings → **Variables and Secrets**, тип **Text**, не Secret). Тогава
съобщението в самия интерфейс носи текста на грешката:

```
Сървърна грешка: Error: D1_ERROR: no such table: users
```

**Махни я, щом приключиш.** Грешките на D1 и на `fetch` носят имена на
таблици и адреси — това не е за пред клиенти.

Секретите се задават **веднъж** и преживяват деплоите — за разлика от
`vars`, които идват от `wrangler.jsonc` при всяко качване.

## 4. Домейнът

Worker → **Settings** → **Domains & Routes** → Add custom domain.

После оправи `PUBLIC_SITE_URL` в `wrangler.jsonc` и в `src/data/site.mjs`,
защото от тях се смятат каноничните адреси, sitemap-ът и — важното — адресът
за връщане на Google OAuth.

## 5. Google Search Console и Analytics

> **Прави нов проект.** Настройките за съгласие — име, обхвати, публикуване,
> проверка — са на ниво **проект** и се споделят от всички OAuth клиенти в
> него. В чужд проект клиентите ще виждат името на онова приложение на екрана
> за одобрение, а забравен чувствителен обхват влачи и неговия таван от 100
> потребителя, макар тук да трябва само Search Console.

### Ако квотата за проекти е свършила

Изтриването **не помага днес**: проект в процес на изтриване продължава да
заема квота през целите 30 дни. Работят други две неща:

| Вариант | Чакане | Бележка |
| --- | --- | --- |
| **Преизползване на неползван проект** | няма | Преименуваш и разчистваш — виж долу |
| Заявка за по-голяма квота | ~2 работни дни | IAM & Admin → Quotas; важи и на безплатен план |
| Чакане на изтриването | 30 дни | Последна възможност |

Преизползването е безопасно, стига проектът да се разчисти.
**Идентификаторът на проекта е вечен** и не се сменя — но никой не го вижда.
Потребителят вижда името от **Branding**, тоест разчистен стар проект е
неразличим от нов.

Избери такъв без прикачено таксуване и без публикувано приложение, после по ред:

| Къде | Какво да махнеш |
| --- | --- |
| IAM & Admin → Settings | Преименуваш проекта на този продукт |
| Auth Platform → **Data Access** | **Всички стари обхвати.** Това е важното — забравен чувствителен обхват ти носи проверка и таван от 100 |
| Auth Platform → **Clients** | Старите OAuth клиенти; нов се прави на стъпка 6 |
| Auth Platform → **Audience** | Старите тестови потребители; провери състоянието на публикуване |

> Преди да се хванеш за даден проект — виж дали е бил **проверяван** за
> чувствителни обхвати. Смяна на обхвати или на брандинг при проверен проект
> може да го върне в ревю, тоест ще чакаш Google за проект, който си избрал
> точно за да не чакаш. Каквото пише Testing и непроверено, е свободно.

Менюто се казва **Google Auth Platform** (по-рано „OAuth consent screen“) и е
разделено на четири: Branding, Audience, Data Access, Clients.

1. В [Google Cloud Console](https://console.cloud.google.com/) създай проект.
2. Включи **Google Search Console API**. (Analytics Data API и Analytics
   Admin API — само ако ще пускаш и Analytics.)
3. **Google Auth Platform → Branding**: име на приложението и имейл за
   поддръжка. Това вижда потребителят, когато одобрява — сложи името на
   продукта, не „My Project 12345“.
4. **Google Auth Platform → Data Access** → Add or remove scopes:
   - `https://www.googleapis.com/auth/webmasters.readonly`

   Само този. Приложението иска Analytics единствено ако зададеш
   `GOOGLE_ENABLE_ANALYTICS=1` — виж защо по-долу.
5. **Google Auth Platform → Audience**: тип **External**, после
   **„Publish app“**, за да мине от **Testing** в **Production**.

   Това е стъпката, която се пропуска най-често, а без нея свързват само
   изрично изброените тестови акаунти в **Audience → Test users** — най-много 100. Таванът е заради
   състоянието Testing, не заради обхвата, тоест важи и при Search Console.

   Публикуването **не иска проверка от Google**, докато обхватите са
   нечувствителни, и потребителите **не виждат предупреждение за
   непроверено приложение**. Тоест: едно натискане, без чакане.

   > **След публикуването „Audience“ пак показва „0 users / 100 user cap“.**
   > Панелът **OAuth user cap** се вижда винаги — и при проверени приложения,
   > пише го в самия текст на Google. Таванът важи само за **неодобрени
   > чувствителни или ограничени** обхвати; при нечувствителни е екран без
   > последствие. Провери го за твоя проект в **Data Access**: обхватите там
   > са разделени на Non-sensitive, Sensitive и Restricted, и това е
   > единственият отговор, който важи за теб.
   >
   > **Не натискай „Back to testing“.** То връща състоянието, при което
   > таванът е истински.
   >
   > Едно нещо в текста заслужава внимание за после: таванът е **за целия
   > живот на проекта и не се нулира**. Затова преизползван проект се
   > разчиства, преди да се ползва — брояч, натрупан от старо приложение,
   > не се връща назад.

6. **Google Auth Platform → Clients** → Create client, тип
   **Web application**, с authorized redirect URI:
   `https://ТВОЯТ-ДОМЕЙН/api/google/callback`

   Адресът трябва да съвпада **знак по знак** с `PUBLIC_SITE_URL` плюс
   `/api/google/callback`; Google отхвърля всичко друго.
7. Подай `GOOGLE_CLIENT_ID` и `GOOGLE_CLIENT_SECRET` като секрети (стъпка 3).

**Няма API ключ.** Search Console чете лични за потребителя данни, затова
API-то работи само с OAuth — статичен ключ няма как да важи. Клиентът е
**един за цялото приложение**, не по един на клиент: всеки потребител просто
натиска „Свържи Google“ и одобрява. Безплатно е и не иска карта или включено
таксуване.

### Кой може да свърже акаунта си — прочети преди да пуснеш клиенти

Не всеки, и това не се оправя от кода.

Докато **Audience** е в режим **Testing**, свързват само изрично добавените
тестови потребители — таванът е **100** и Google не го вдига. Затова стъпка 5
по-горе не е по избор.

В **Production** таванът пада. Google проверява приложението само ако то иска
„чувствителни“ обхвати; при нечувствителни публикуването е едно натискане.

Двата ни обхвата не са в една категория:

| Обхват | Категория | Какво значи |
| --- | --- | --- |
| `webmasters.readonly` (Search Console) | нечувствителен | работи за всички без проверка |
| `analytics.readonly` (Analytics) | **чувствителен** | иска проверка на приложението преди публичен достъп |

Тоест **Search Console работи за неограничен брой клиенти веднага**, а
Analytics — не, докато приложението не мине проверка (доказана собственост
върху домейна, политика за поверителност на живо, видео демонстрация на
потока и обосновка защо е нужен обхватът).

Затова приложението иска **само Search Console по подразбиране**. Нищо не се
маха от кода: Analytics се включва с променливата `GOOGLE_ENABLE_ANALYTICS=1`
в Settings → Variables and Secrets, след като проверката мине. Докато е
изключена, инструментите `ga4_*` не се предлагат и на модела — инструмент,
който винаги отговаря „няма достъп“, е обещание, което ботът не може да спази.

### Планът за Analytics: по-късно и само за платените планове

Решението е взето: пуска се със Search Console, а Analytics идва след
проверката — и то като функция на Pro и Business, не за всички.

`GOOGLE_ENABLE_ANALYTICS` в сегашния си вид е **общ ключ за инсталацията**, не
за план. Като дойде моментът, това са трите места:

1. `analyticsEnabled(env)` в [`src/lib/google.ts`](../src/lib/google.ts) става
   функция и от плана — нещо като `analyticsFor(env, user.plan)`.
2. `googleScopes` вече се вика от `connect.ts`, който **вижда потребителя**,
   тоест обхватът може да се иска само за платен план. Това е нормалният
   модел на постепенно разрешаване.
3. `toolSchemas(env)` в [`src/lib/tools.ts`](../src/lib/tools.ts) също трябва
   да получи плана, за да не вижда моделът инструменти, които няма да сработят.

> **Внимание при смяна на обхвати след като има клиенти.** Refresh токенът
> носи обхватите, с които е издаден. Добавен по-късно `analytics.readonly`
> НЕ важи за вече свързаните акаунти — всеки от тях трябва да свърже наново.
> При надграждане на плана това е приемливо (потребителят и без това прави
> нещо), но при масова промяна е неприятно. Затова и `/api/google/status`
> връща записаните обхвати: по тях се вижда кой има нужда от повторно
> свързване.

Категорията се вижда най-сигурно в самия Google Cloud Console: при добавяне на
обхват той е отбелязан като Sensitive / Restricted / нищо. Класификациите се
менят — `webmasters.readonly` беше чувствителен до 2024 г. Проверявай там,
преди да разчиташ на таблицата горе.

> Приложението не се чупи без Analytics: инструментите `ga4_*` връщат ясно
> „няма връзка“, а всичко останало работи.

## 6. Проверката след първия деплой

Отвори три адреса в браузър, без да си влязъл:

| Адрес | Какво трябва да стане |
|---|---|
| `/` | началната страница се показва |
| `/tablo/` | препраща към `/vhod/` — таблото не пуска излязъл посетител |
| `/api/chats` | `{"ok":false,"error":"Влез в акаунта си."}` |

Препращането и отказът са верните отговори, не грешки. Ако самото `/` дава
грешка, виж дневника в **Workers & Pages** → Worker-ът → **Deployments**.

После:

1. Регистрирай акаунт и добави домейн.
2. **Табло → Двигатели → „Провери моделите“.** Задължителната стъпка. Гледай
   реда „N/M двигателя **наистина търсят“** — само те мерят видимост. Двигател
   с етикет „поиска търсене, но не търси“ отговаря, но мери познатост.
   Поправките са стойност в **Settings → Variables and Secrets**, без деплой.
   Подробностите са в [docs/models.md](models.md).
3. „Нова проверка“ — първата отнема около минута.

## Локална разработка

Не е нужна за пускането — всичко по-горе минава през браузъра. Но ако ще се
пише код:

```bash
npm install
npm run db:migrate:local
npm run dev        # Astro dev сървър — бърз, без Cloudflare binding-и
npm run preview    # wrangler dev — истинският Worker с D1
```

Секретите за локално отиват в `.dev.vars` (в `.gitignore`):

```
SESSION_SECRET="местна-стойност-не-за-продукция"
TOKEN_ENC_KEY="местна-стойност-не-за-продукция"
```

**Workers AI не работи при `wrangler dev --local`** — binding-ът връща
„Binding AI needs to be run remotely“. Чатът и проверката на видимост искат
`npx wrangler dev --remote`. Всичко останало — вход, табло, анализатор,
задачи — работи изцяло локално.

Версията на Node е закована в `.node-version` (24), за да строят CI и
Cloudflare с една и съща — иначе проверката в GitHub не тества това, което
после се качва.
